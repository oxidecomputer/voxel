# Voxel - engineering roadmap

Voxel (Virtual OXide Emulated Laboratory): an operator-focused evolution of a4x2
for planning, commissioning, and evolving Oxide deployments - operators pick an
Oxide platform *version* + a topology and launch, GNS3/Container-Lab style.

> The product docket (networking-docket -> voxel.html) is the canonical plan.
> This file is the engineering roadmap + decisions made while building it.

## Done

- **Snapshot-first image build** (`voxel-image/`): generic single-node falcon
  builder (`VBUILD_IMAGE` / `VBUILD_CARGO_BAY` / `INSTALL_SCRIPT`) + Helios
  orchestrator. Two `CAPTURE_MODE`s - `raw` (portable `.raw.xz`, streaming
  re-import) and `zfs` (fast box-local `zfs send/recv`).
- **`voxel-cp` image** - Helios + version-pinned Oxide control plane
  (`install-cp.sh`, baked through `omicron-package unpack`). Validated: boots
  with all 16 zones intact.
- **`voxel-frr` image** - Debian + FRR for routers (`install-frr.sh`, `bgpd`
  enabled). Validated: boots to FRRouting 10.3.
- **`voxel-config`** (pure Rust, Mac-testable): generates the unnumbered-BGP
  RSS `config-rss.toml` on the fly; golden test reproduces a known-good config.
- **★ First full rack bring-up -> live Nexus (2026-06-15)** - the MVP. Unnumbered
  4-gimlet (g0,g1,g3 RSS) rack on the Helios box: 7/7 propolis, RSS converged, full
  control plane up (switch, internal/external DNS, NTP, CockroachDB, ClickHouse,
  Crucible, Oximeter, **Nexus** - 107 zones). Two blockers cleared to get here:
  (1) **sidecar_lite mismatch** - baked dendrite emits RFC 5549 `forward_v6` routes
  the old `b96d785` SoftNPU program panics on; `prep.sh` now pins the
  `forward_v6`-capable rev `bf44a554`. (2) **boundary-NTP time sync** - the slim
  topology dropped a4x2's `cfw` NAT node, so the rack had no internet egress for its
  NTP upstream; `router-launch.sh` now does `rp_filter=0` + NATs rack traffic out
  each router's lab uplink. Both are launch-time scaffolding to fold into the image
  (see De-a4x2-ify): the sidecar belongs baked in `voxel-cp`; NAT egress is a
  topology concern (add a NAT/edge node, or keep the per-router masquerade).

  dataplane. Also note voxel is a *functional* sim, not perf-faithful, so crucible
  numbers here reflect emulation overhead, not real hardware. Parked.

  against the `voxel-frr` image.

  post-`unpack` (it's a zone tarball; no SMF-property config). Fix: give sp-sim

  generic (multi-sled) image; today's prototype reuses g0/switch0-specific config.
- **Harden the bring-up** - the MVP converged but with launch-time hand-holding;
  make it repeatable: bake `sidecar_lite` into `voxel-cp` (drop the `prep.sh`

  smooth the per-sled config/identity staging so a clean `prep && launch` just works.
- **De-a4x2-ify - cut the cargo-bay dependency** *(milestone, see below)* - bake
  tools + `sidecar_lite` into the image, generate identity/config, and build
  `voxel-cp` reproducibly off any released omicron artifact set (no a4x2 build
  output, no build-from-source). This is the one that makes Voxel ≠ a4x2.

## Deferred

- **High-fidelity SP/RoT emulation (Renode)** - *committed direction, not yet
  scheduled.*
  - **★ FEASIBILITY SPIKE = GO (2026-06-16).** Renode v1.16.1 (arm64-native .NET,
    `/Applications/Renode.app`) boots a real Hubris SP image. Recipe: built
    `app/gimletlet/app.toml` -> `final.elf` (`cargo xtask dist`, nightly-2025-07-20);
    booted via Renode's bundled `scripts/single-node/nucleo_h753zi_hubris.resc`
    idiom (board `platforms/boards/nucleo_h753zi.repl` + `cpu VectorTableOffset
    0x8000000` in a reset macro + `sysbus LoadELF`). Result: ~28.7M instructions in
    5 s virtual, PC in app code, the net task configuring the ethernet MAC - i.e.
    kernel boots + schedules tasks. **Renode's Cortex-M7 model handles Hubris where
    QEMU can't** (Hubris FAQ: "QEMU? Not usefully, no"). Antmicro even ships a
    `hubris-stm32h753-udprpc` demo, so it's a maintained path. The SP is proven;
    the RoT (LPC55/TrustZone) remains the open, harder piece.
  Replace the protocol-level `sp-sim` + mocked attestation with real
  **Hubris firmware** running under [Renode]: the SP (STM32H753, Cortex-M7) and
  the RoT (NXP LPC55S69, Cortex-M33 + TrustZone), modeling the SP↔RoT SPI link
  and SP↔MGS management ethernet. **Goal: validate real update, firmware, and
  attestation / trust-quorum flows end-to-end** - the code paths the mock can't
  exercise. Net-new work: a Renode platform for the SP/RoT boards + a Hubris
  target; verify Renode's LPC55S69/TrustZone coverage. (QEMU is weaker here:
  partial STM32H7 peripherals, poor M33/TrustZone story, DIY interconnect.)
  - **Unblocks `pilot` on the switch** (investigated 2026-06-16): racklette switches
    run `/usr/bin/pilot` for `pilot host login`, etc. We built `pilot` from
    `~/oxide/pilot` and ran it in our live `oxz_switch`: it works, but its
    `detect_dendrite()` keys *solely* on the presence of `gimletNN` network
    interfaces (the per-cubby SP-management VLANs real dendrite creates), and
    discovers SPs via its own UDP protocol over them. Our SoftNPU sim switch zone
    has only **data-plane** `tfport*` interfaces - SP comms run `mgs-sim ↔ sp-sim`
    over loopback ports - so pilot finds no SPs (`sp ls` demands `-i`, `host ls`
    refused). pilot is also config-less (no `/etc/pilot.toml` needed; racklettes
    have none). So "pilot on the voxel switch" is gated on giving the switch zone
    `gimletNN` SP-management-VLAN plumbing to each `sp-sim` - i.e. this SP-emulation
    work, or a `faux-mgs`-based bridge (faux-mgs *can* reach `sp-sim`).

- **Multi-rack on one box + Voxnet (rack-to-rack)** - *committed direction, not
  yet scheduled.* Run two (or more) racks on a single Helios box and network them
  together as a customer would across racks/sites.
  - **Already handled:** falcon namespaces every link by deployment name
    (`voxel_<node>_<...>`; `--name` / `VOXEL_NAME`), so the VNIC/simnet layer
    doesn't collide between racks. The `VNIC busy` error we hit was stale state
    from a half-torn-down *single* rack (`voxel destroy` clears it), **not** a
    co-tenancy limit. The MGS-sim loopback ports (`[::1]:333xx`) are switch-zone-
    local and the `oxz_*` zones are nested in the propolis guests, so nothing
    there collides at host scope either.
  - **Blocker #1 - shared external identity (the real one):** every launch bakes
    the same external prefix (`198.51.100.0/24`), `rack_subnet`
    (`fd00:17:01:d00::/56`), service pool, and bootstrap subnets, and
    `set_external_route` installs a single host route `infra_prefix -> ce`. Two
    racks both originate `198.51.100.0/24` and both want that route. Fix: make the
    `network` block per-instance (distinct external prefix, rack subnet, service
    pool, bootstrap base, upstream ASNs). It's typed config now, so this is
    plumbing - not the rearchitecture it would have been in a4x2.
  - **Blocker #2 - relative on-disk state:** `./cargo-bay/<node>` (hardcoded) and
    `.falcon` are cwd-relative, so two racks from the same dir stomp each other.
    Namespace both by `--name` (or run each from its own dir).
  - **Heterogeneous / smaller racks:** allow dropping specific sleds (e.g. leave
    out `g2` to save RAM while keeping the `g0`+`g3` scrimlet pair). Today
    `topology.sleds` is a *count* that expands to a contiguous `g0..g{n-1}`, so
    you can't drop `g2` specifically without losing `g3`. Needs an explicit sled
    set (named sleds + per-sled role) rather than a count. Each 4-sled rack is
    ~4×(8 vCPU/8 GB) + routers, so trimming sleds is how two racks fit at all.
  - **Voxnet - the actual feature:** once two racks coexist with distinct
    networks, wire their customer edges together (router-to-router, ideally over
    the highest-bandwidth path the box affords) to model multi-rack / multi-site
    topologies a customer would build - cross-rack BGP, a shared transit fabric,
    or a simulated WAN. This is where Voxel goes past "one virtual rack" to "a
    virtual datacenter."

## Design decisions

- **Unnumbered BGP always.** Verified end-to-end (RSS `addr = "unnumbered"` +
  `addrconf` + `infra_ip_first/last = "::"`; mgd `UnnumberedNeighbor` + NDP +
  RFC 5549; FRR `neighbor <iface> interface remote-as external`). Removes the
  per-link addressing plan.
- **Routers = FRR-on-Debian** (`voxel-frr`), config generated on the fly. Arista
  cEOS is bring-your-own (proprietary; not built/shipped).
- **Generic images + launch-time config.** Images carry binaries only; all
  topology/identity config (RSS, FRR, sprockets, SMBIOS, sp-sim/mgs-sim, sidecar
  load) is generated and applied at launch. One image serves every topology.
- **Sidecar = SoftNPU** (falcon `softnpu_link` + `sidecar-lite` artifacts, loaded
  via `scadm` at launch). **SPs = simulated** (`sp-sim` + MGS sim-mode), until
  the Renode work above.

## Architecture decision (RESOLVED): config-gen is typed + travels per publish

Hand-templating omicron config on the host was wrong - it coupled Voxel to the
schema and cost an hour of one-field-per-launch thrash (`bootstrap_discovery` vs
`bootstrap_sleds`, tagged-vs-string addrs, `router_lifetime`, ...). Two decisions:

1. **Typed, not templated.** Build omicron's OWN config type (`RackInitializeRequest`
   in the light `bootstrap-agent-lockstep-types` crate - only `sled-hardware-types`
   dep; config-rss.toml is its dev/test file form) and let serde emit the TOML.
   This is exactly what `~/oxide/topology-quest` does (`PutRssUserConfigInsensitive`
   + `toml::to_string`); the *types are the schema*, so mismatches are compile
   errors, not runtime parse failures.
2. **No host version pin - version-match per publish.** The config-gen is built
   against the SAME omicron as the image and travels with it (ultimately baked in ->
   in-image `voxel-init`). The host tool stays version-agnostic and passes a small
   topology descriptor; `voxel-cp-19.4` carries 19.4's config-gen, `voxel-cp-20rc1`
   carries 20rc1's, etc. - correct by construction, no global pin.

Why not the topology-quest crate wholesale: different topology class (CLOS-of-racks
vs single-rack+routers), it emits the *insensitive* wicket config (no certs/silo,
we need the full file), and it pins one rev. We reuse its *pattern* + network-config
construction code. Per-sled identity injection itself is fine and irreducible (a4x2
bakes it into four package builds; one image + descriptor is lighter) - the issue
was the SOURCE (hand-templated), now fixed by typed-per-publish.

## De-a4x2-ify - cut the cargo-bay dependency (milestone)

What actually hurts about a4x2 is its **moving parts at deploy time**: build from
source, a sprawling cargo-bay of tools/keys/configs/artifacts staged per node, and
fetch-at-launch SoftNPU artifacts. Voxel's thesis is the inverse - a few
**self-contained, version-matched images** + a tiny generated descriptor. The first
bring-up leans on `/opt/testbed/a4x2/cargo-bay` as a deliberate crutch; this
milestone removes it.

**Definition of done:** `prep.sh` reads **no** a4x2 build output, and a clean
checkout can build a `voxel-cp` image from *any* omicron release and launch a rack.
If this doesn't land, Voxel has just reskinned a4x2 - the failure mode this section
exists to prevent.

**A. Bake binaries + artifacts into the image** (version-locked to the control
plane, shipped as one unit - not fetched, not borrowed):
- omicron CLI tools (`omicron-package`, `xtask`, `xtask-downloader`) -> into
  `voxel-cp` via `install-cp.sh`; cargo-bay stops mounting a4x2's `omicron/`.
- **`sidecar_lite` (`scadm` + `libsidecar_lite.so`) -> baked into `voxel-cp`**,
  version-matched to the image's dendrite. *(2026-06-15: the unnumbered scrimlet
  crash was exactly this mismatch - a4x2-main's `b96d785` sidecar lacks the
  `forward_v6` action the image's dendrite emits for RFC 5549 v4-over-v6 routes.
  Fix proven on the box by pinning the matching rev `bf44a554`; it currently lives
  as a temporary `SIDECAR_LITE_REV` fetch in `prep.sh` - bake it instead.)* a4x2
  fetches this at deploy (`fetch-softnpu-artifacts.sh`); voxel should carry it.
- recovery-silo hash + internal-services defaults -> owned by voxel-config, not
  copied from a4x2.

**B. Generate per-node identity + config** (no static a4x2 files):
- `prep.sh` copies a4x2 **static `gN-config.toml`** -> generate per-sled sled-agent
  config from the topology descriptor (model A) / typed expansion (model B).
- sprockets keys + SMBIOS identity -> generated per node by voxel.
- **baked g0/switch0 `sp-sim`/`mgs-sim`** -> SMF-property config (mirror `mgs`) or
  generate; also the seam for a real software RoT / the Renode RoT.

**North star - reproducible image build off any omicron release.** Point
`install-cp.sh` at a *released* omicron artifact set (a version tag -> published
zones + tools + matching sidecar rev), not a local build, so
`build-image.sh VERSION=<rel>` yields `voxel-cp-<rel>` deterministically. This is
the "publish a 19.4, a 20rc1, ... on the fly" model (see the config-gen decision
above) applied to the whole image - the binaries, the sidecar, and the config-gen
all travel together, version-matched by construction.

## Quality-of-life (from docket)

- a4x2 "murders disks" - reduce write amplification on the host pool.
- Cold boot broken - sled-agent assumes ephemeral (ramdisk) state that persists
  in a4x2 because disks are regular VM images. Lever: boot the OS from a
  read-only/ramdisk image + truly-ephemeral data vdevs.
- CR nodes lose their default route to DHCP over time (mgmt-NIC DHCP client;
  separate from BGP - `nodefaultroute` / mgmt VRF).
